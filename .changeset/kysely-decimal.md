Add a `decimal` option to `kyselyTypePlugin`. With `decimal: true`, the generated table types give decimal columns the type `Decimal` from decimal.js on read and `Decimal | string` on write, and the generated `getDB` returns `Decimal` values and accepts `Decimal` as a query parameter, sent without an exponent. Columns are found by the column types the query result reports, so an alias such as `select price as p` and an aggregate such as `sum(price)` are converted too, and float and integer columns are not. Every result column reported as numeric becomes a `Decimal`, including aggregates and arithmetic over decimal columns such as `sum(price)` and `price * 2`; aggregates over integer or float columns stay numbers. Kysely types an aggregate such as `sum()` as `string | number | bigint`. A decimal field inside an object stays a string. It works with `distPath` only, and combining it with `contentMapper: true` is rejected.

`createGetDB` takes a `decimal` option (the `Decimal` class), and `TailorDBInsertable`, `TailorDBSelectable`, and `TailorDBUpdateable` take a third `IsDecimal` type parameter that follows the same mapping. `TailordbQueryResult` has a `fields` listing each column's name and PostgreSQL type name, so a hand-written stand-in for `tailordb.Client` has to return it; `mockTailordb` returns an empty list.

A migration generated with `decimal: true` types its `db.ts` with `Decimal` columns, records `decimal` in `diff.json`, and runs its script with `Decimal` values on deploy; its generated `migrate.test.ts` passes the `Decimal` class to `createKyselyPGlite`. Only such a migration is written as format version 9, which older SDK versions refuse to read; other migrations keep format version 8. `mockTailordbWithPGlite` returns the column names and PostgreSQL type names next to the rows, and `createKyselyPGlite` accepts a `decimal` option.
