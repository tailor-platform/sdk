**Breaking change (beta)**: `tailor deploy` and `tailor tailordb migration validate` now check a deployed TailorDB namespace that has no migration checkpoint yet against migration `0000`, as `tailor tailordb migration test` already did. Previously they skipped the check, so the first deploy after adding migrations to an existing project overwrote tables that differed from `0000`, for example deleting a field added in the console. When the tables differ, `tailor deploy` stops with `MIGRATION_REMOTE_DRIFT` and `migration validate` fails, and both suggest the two ways to reconcile them before the first deploy with migrations: overwrite the deployed tables with `tailor tailordb migration sync 0000`, or update the local tables to match the deployed ones and recreate `0000` with `tailor tailordb migration generate --init`. A deploy that stopped after creating only some of the tables also needs `migration sync 0000`. `migration validate --json` no longer reports `skipped: "no_migration_label"`: a namespace with tables but no checkpoint reports `checkpointUnset: true`, and one without tables reports `skipped: "not_deployed"`, which `migration test` now refuses as not deployed.
