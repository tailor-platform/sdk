Profiles & the default machine user

We start with "what is a profile?" and the handy .envrc combo, then move on to the main act: pinning a default machine user so the wrong identity can't be used by accident. Every command has a Copy button for one-click copy.

Part 1 — What is a profile? / The .envrc combo

iA profile = a named "user × workspace" pair
So you don't retype -w <workspace-id> every time. After authenticating with tailor-sdk login, a profile decides which workspace your commands talk to. Start by listing them: 
tailor-sdk profile list
Shows: a table of name / user / workspaceId / permission.
iCreating one (log in first)
Log in to authenticate the user, then a profile binds a workspace to a name. 
tailor-sdk login
tailor-sdk profile create mu-demo -u akira_higuchi@tailor.tech -w 5d80e666-2f32-499f-b878-213229a558b8 -m manager-machine-user
(This is exactly the command Part 2 / Step 1 runs — shown here for the shape; don't create it twice.) For a workspace you don't want to write to (e.g. production), add --permission read so all write commands are blocked while the profile is active — see Part 3.
iHow the active profile is chosen (precedence)
--profile <name> > the TAILOR_PLATFORM_PROFILE env var > the current login. Switching per command with the flag (run from example/; -m / -c are this project's specifics): 
tailor-sdk query --engine gql -q '{ users(first: 1) { edges { node { name } } } }' --profile show-and-tell -m manager-machine-user -c tailor.config.ts
iHandy: .envrc + direnv to switch environments just by "cd"
Put an .envrc in each directory and pin the profile via an env var. direnv loads it the moment you enter the directory, so directory = environment switches automatically. Split dev / stg / prod into separate directories (worktrees) and you stop targeting the wrong workspace. 
# .envrc (place it in the directory)
export TAILOR_PLATFORM_PROFILE="show-and-tell"

# optional default machine user for query / workflow start / etc. (used in Part 2)
export TAILOR_PLATFORM_MACHINE_USER_NAME="manager-machine-user"
You must approve it once with direnv allow. This show-and-tell worktree itself uses .envrc with TAILOR_PLATFORM_PROFILE="show-and-tell" (live example).

Part 2 — Prevent identity mix-ups with a default machine user (live demo)

The main act: bake a default machine user into the profile and pin it with --machine-user-override deny, so a shared workspace / CI can't run commands under the wrong identity.

Workspace: sdk-show-and-tell WS ID: 5d80e666-2f32-499f-b878-213229a558b8 Machine user: manager-machine-user User: akira_higuchi@tailor.tech
⚠️ Run everything from the example/ directory (token/query commands pass -c tailor.config.ts to point at the config explicitly).

0. Go to the working directory

0Into the show-and-tell worktree's example/ 
cd /Users/toiroakr/workspace/sdk-bare/show-and-tell/example

1. Setup: create a profile with a default machine user

1profile create (bake in the default machine user)
At this point machineUserOverride = allow (override permitted). 
tailor-sdk profile create mu-demo -u akira_higuchi@tailor.tech -w 5d80e666-2f32-499f-b878-213229a558b8 -m manager-machine-user
Expect: a table showing machineUser = manager-machine-user / machineUserOverride = allow.
1profile list (confirm) 
tailor-sdk profile list
Expect: mu-demo appears in the list.

2. Fallback: omit the machine user and the default is used

2query (no machine user) → runs as the profile's default
Run a GraphQL query without passing a machine user anywhere. env -u TAILOR_PLATFORM_MACHINE_USER_NAME temporarily drops the env var this worktree's .envrc sets, to create a truly "unspecified" state. 
env -u TAILOR_PLATFORM_MACHINE_USER_NAME tailor-sdk query --engine gql -q '{ users(first: 3) { edges { node { name role } } } }' -p mu-demo -c tailor.config.ts
Expect: users returned as JSON (executed as the default manager-machine-user).

3. Lock it: set override to deny

3profile update --machine-user-override deny
deny requires --machine-user. From now on, any different machine user is rejected. 
tailor-sdk profile update mu-demo -m manager-machine-user --machine-user-override deny
Expect: updates to machineUserOverride = deny.

4. The point: a different machine user fails immediately

4aPass a different machine user on the CLI → DENIED 
tailor-sdk query --engine gql -q '{ users(first: 3) { edges { node { name role } } } }' -m other-user -p mu-demo -c tailor.config.ts
Expect: Error [PROFILE_MACHINE_USER_OVERRIDE_DENIED] — "fixes the machine user to 'manager-machine-user'".
4bPass it via the env var → DENIED too 
TAILOR_PLATFORM_MACHINE_USER_NAME=other-user tailor-sdk query --engine gql -q '{ users(first: 3) { edges { node { name role } } } }' -p mu-demo -c tailor.config.ts
Expect: same PROFILE_MACHINE_USER_OVERRIDE_DENIED. The pin holds for both CLI and env.

5. A value matching the default still works

5Pass the same machine user as the profile's default → succeeds 
tailor-sdk query --engine gql -q '{ users(first: 3) { edges { node { name role } } } }' -m manager-machine-user -p mu-demo -c tailor.config.ts
Expect: users returned as JSON (deny only rejects a different value).

6. (Optional) Unlock

6profile update --machine-user-override allow 
tailor-sdk profile update mu-demo --machine-user-override allow
Expect: back to machineUserOverride = allow; overrides are permitted again.

7. Cleanup

7Delete the demo profile 
tailor-sdk profile delete mu-demo
Expect: Profile "mu-demo" deleted successfully.

Part 3 — Read-only profile + read-only machine user (staging/prod & AI)

Two complementary guards for an environment you want to inspect but never mutate — handy when you point a local AI agent or MCP server at staging.

⚠️ Run from example/. We use the sdk-show-and-tell workspace as a stand-in for "staging".
1Layer 1 — create a read-only profile (CLI guard)
With --permission read, write commands (deploy, truncate, workflow start, secret set, ...) fail fast; reads like query / *list / describe still work. 
tailor-sdk profile create stg-readonly -u akira_higuchi@tailor.tech -w 5d80e666-2f32-499f-b878-213229a558b8 --permission read
Expect: created with permission = read.
2A write command is blocked 
tailor-sdk deploy -c tailor.config.ts --dry-run --profile stg-readonly
Expect: Error [PROFILE_READONLY] — "blocks platform-state mutations (apply, create/update/delete, deploy, ...). Application-data operations remain available because their permissions are governed by the machine user."
3A read command still works 
tailor-sdk query --engine gql -q '{ users(first: 1) { edges { node { name } } } }' -m manager-machine-user -p stg-readonly -c tailor.config.ts
Expect: users returned as JSON.
4Layer 2 — pin the machine user (server-side guard)
The profile stops the CLI; the machine user's own permissions stop the server. In real staging, point this at a machine user whose TailorDB / IdP permissions only grant read (defined in tailor.config.ts). Here we pin manager-machine-user as a stand-in: 
tailor-sdk profile update stg-readonly -m manager-machine-user --machine-user-override deny
With a read-only-role machine user, even a GraphQL mutation via query is rejected by the platform, and deny means the identity can't be swapped.
5Cleanup 
tailor-sdk profile delete stg-readonly
Expect: Profile "stg-readonly" deleted successfully.
iWhy this fits AI agents / MCP
AI agents and MCP servers increasingly run queries against real environments (RAG, analytics, debugging). Point your local agent at this read-only profile + read-only machine user and:
  • it can read / inspect staging data, but cannot deploy, mutate, or delete;
  • a prompt injection or a buggy tool call can't escalate to writes;
  • --machine-user-override deny means it can't swap to a more privileged machine user.
One read-only identity, enforced on both the CLI and the platform — scoped to your own local setup.
Talking points (wrap-up)
  • Precedence is --machine-user > TAILOR_PLATFORM_MACHINE_USER_NAME > the profile's default.
  • --machine-user-override deny forbids "acting as a different user" from both the CLI and the env var, at the config level.
  • It applies to application-data commands: query / workflow start / function test-run / machineuser token.
  • Profiles are local per-developer config, so think of this as a personal safety guard: it stops your own commands — and any AI agent / MCP you run locally — from acting as the wrong identity. It's not an org-wide policy others can't bypass.
