Tailor Platform SDK — Show & Tell

Profiles, Platform Settings
& Machine Users

Four capabilities built into profiles: save the Platform API connection so switching profiles also switches environments; lock a profile to read-only so write commands fail fast; pin a default machine user; and deny overrides to prevent identity escalation. Every command has a copy button.

Part 1

Feature Overview

Profiles, platform settings, default machine users, override deny, and the .envrc combo — concepts before commands.

Profiles
A profile is a named "user × workspace" pair
After authenticating with tailor-sdk login, a profile holds which workspace your commands talk to. No more repeating -w <workspace-id> on every command — switching is a single --profile flag away. 

tailor-sdk profile list
→ Shows a table of name / user / workspaceId / permission / machineUser.
Activation precedence
The active profile for a command resolves in this order:
1st (wins) --profile <name> flag
2nd TAILOR_PLATFORM_PROFILE env var
3rd Current login (state from tailor-sdk login)
Platform settings
Save the Platform API connection on a profile
When workspaces live on a non-default Tailor Platform instance (custom domain), pass --platform-url, --oauth2-client-id, and --console-url to profile create. After that, switching profiles switches the entire environment — API URL, OAuth2 client, and Console — without ever re-exporting env vars.

First-time setup (once per Platform instance): 
export TAILOR_PLATFORM_URL=https://<org>.tailor.tech
export TAILOR_PLATFORM_OAUTH2_CLIENT_ID=<oauth2-client-id>
export TAILOR_PLATFORM_CONSOLE_URL=https://console.<org>.tailor.tech

tailor-sdk login
tailor-sdk profile create staging \
  -u you@example.com \
  -w <staging-workspace-id> \
  --platform-url "$TAILOR_PLATFORM_URL" \
  --oauth2-client-id "$TAILOR_PLATFORM_OAUTH2_CLIENT_ID" \
  --console-url "$TAILOR_PLATFORM_CONSOLE_URL"

unset TAILOR_PLATFORM_URL TAILOR_PLATFORM_OAUTH2_CLIENT_ID TAILOR_PLATFORM_CONSOLE_URL
Day-to-day — no env vars needed: 
tailor-sdk deploy -p staging
tailor-sdk open -p staging
tailor-sdk login -p staging    # refresh token without re-exporting URLs
--platform-url, --oauth2-client-id, and --console-url also read from TAILOR_PLATFORM_URL, TAILOR_PLATFORM_OAUTH2_CLIENT_ID, and TAILOR_PLATFORM_CONSOLE_URL respectively — so if those env vars are already exported, the flags can be omitted from profile create entirely.

To clear a saved setting, pass an empty string: profile update staging --platform-url ""
Machine users
Default machine user — the fallback when none is specified
Pass -m <machine-user> when creating a profile to bake in a default. When no machine user is given on the command, the profile's default is used automatically.

Machine user resolution follows the same layered structure:
1st (wins) --machine-user <name> flag
2nd TAILOR_PLATFORM_MACHINE_USER_NAME env var
3rd Profile default (set with -m at create time)
--machine-user-override deny — pin the identity
Set profile update --machine-user-override deny and the profile rejects any attempt to use a different machine user — whether it comes from a CLI flag or an env var. The error is immediate: PROFILE_MACHINE_USER_OVERRIDE_DENIED.

Passing the same value is fine — deny only blocks switching to a different identity.

Applies to: query / workflow start / function test-run / machineuser token and all other application-data commands.
.envrc combo (direnv)
Switch environments just by cd-ing
Drop an .envrc in each directory and direnv loads it the moment you enter. Split dev / stg / prod into separate directories (worktrees) and directory = environment — accidental deploys to the wrong workspace stop happening. 
# .envrc (place it in the directory)
export TAILOR_PLATFORM_PROFILE="show-and-tell"

# default machine user can also be set via env var
export TAILOR_PLATFORM_MACHINE_USER_NAME="manager-machine-user"
Requires direnv allow once. This show-and-tell worktree itself uses TAILOR_PLATFORM_PROFILE="show-and-tell" in its .envrc (live example).

Read-only profile + read-only machine user

Two complementary guards for a workspace you want to inspect but never mutate — handy when you point a local AI agent or MCP server at staging.

Workspace: sdk-show-and-tell WS ID: 5d80e666-2f32-499f-b878-213229a558b8 Machine user: manager-machine-user User: akira_higuchi@tailor.tech
⚠ Run everything from example/. Token/query commands pass -c tailor.config.ts to point at the config explicitly.
0. Working directory
[00] Into the show-and-tell worktree's example/ 
cd /Users/toiroakr/workspace/sdk-bare/show-and-tell/example
Layer 1 — CLI guard (read-only profile)
[01] Create a profile with --permission read
With --permission read, write commands (deploy, truncate, workflow start, secret set, …) fail fast. Reads like query / *list / describe still work. 
tailor-sdk profile create stg-readonly -u akira_higuchi@tailor.tech -w 5d80e666-2f32-499f-b878-213229a558b8 --permission read
✓ Expect: created with permission = read
[02] A write command is blocked 
tailor-sdk deploy -c tailor.config.ts --dry-run --profile stg-readonly
✗ Expect: Error [PROFILE_READONLY] — "blocks platform-state mutations (apply, create/update/delete, deploy, ...). Application-data operations remain available because their permissions are governed by the machine user."
[03] A read command still works 
tailor-sdk query --engine gql -q '{ users(first: 1) { edges { node { name } } } }' -m manager-machine-user -p stg-readonly -c tailor.config.ts
✓ Expect: users returned as JSON
Layer 2 — server-side guard (pin the machine user)
[04] Pin the machine user with override deny
The profile stops the CLI; the machine user's own permissions stop the server. In real staging, point this at a machine user whose TailorDB / IdP permissions only grant read. deny means a prompt injection or a buggy tool call can't swap to a more privileged identity. 
tailor-sdk profile update stg-readonly -m manager-machine-user --machine-user-override deny
✓ Expect: machineUserOverride = deny
Cleanup
[05] Delete the demo profile 
tailor-sdk profile delete stg-readonly
✓ Expect: Profile "stg-readonly" deleted successfully.
AI agents / MCP
[info] Why this matters for AI agents and MCP servers
AI agents and MCP servers increasingly run queries against real environments (RAG, analytics, debugging). Point your local agent at this read-only profile + read-only machine user and:
  • it can read / inspect staging data, but cannot deploy, mutate, or delete;
  • a prompt injection or a buggy tool call can't escalate to writes;
  • --machine-user-override deny means it can't swap to a more privileged machine user.
One read-only identity, enforced on both the CLI and the platform — scoped to your own local setup.
