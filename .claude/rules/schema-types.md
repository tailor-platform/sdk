# Schema Types

## The `src/types/` Directory

`src/types/` contains **only** vinfer-generated types and generic utility types:

| File type        | Example                 | Role                                                                    |
| ---------------- | ----------------------- | ----------------------------------------------------------------------- |
| `*.generated.ts` | `tailordb.generated.ts` | Auto-generated by vinfer from Valibot schemas. **Do not edit manually** |
| `helpers.ts`     | `output`, `Prettify`    | Generic utility types with no domain knowledge                          |

Do not add hand-written domain types here. They belong in the owning layer's
pure type module (see below).

## Pure Type Modules

Hand-written shared types live next to the code that owns them, in **pure type
modules** — files named `types.ts` (or `*.types.ts` under `configure/`):

| Module                                                             | Contents                                                                 |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------ |
| `configure/types/field.types.ts`                                   | Generic field structural types, field options, validation types          |
| `configure/services/tailordb/types.ts`                             | TailorDB minimal structural types, metadata, service config, UX types    |
| `configure/services/auth/types.ts`                                 | Auth input types, user-field type machinery, `ValueOperand`              |
| `configure/services/{idp,secrets,staticwebsite,resolver}/types.ts` | Per-service config input types                                           |
| `configure/config/types.ts`                                        | `AppConfig` and service input types                                      |
| `parser/service/tailordb/types.ts`                                 | Parsed data structures (`TailorDBType`, `ParsedField`, permissions, ...) |
| `parser/service/idp/types.ts`                                      | Normalized IdP permission types shared by parser and CLI                 |
| `plugin/types.ts`                                                  | Plugin authoring types, generation hook contexts, generator config       |
| `runtime/types.ts`                                                 | Runtime principal/env types (`TailorPrincipal`, `TailorEnv`)             |

Rules for pure type modules (enforced by oxlint):

1. **Imports must be type-only** — no runtime imports, so any layer can import
   the module without pulling runtime code into user bundles.
2. **No `valibot` references, even type-only** — a `v.InferOutput` chain would
   load valibot's type machinery into the user's tsc. Schema-derived types
   must go through vinfer generation instead.
3. **No schema imports, even type-only** — importing `**/schema` modules is
   banned for the same reason as above.

Other layers may import pure type modules **type-only**, across boundaries that
are otherwise closed (e.g. `configure` → `parser/**/types`, `cli` →
`configure/**/types`). See the `sdk-internals` rule for the boundary matrix.

## Schema ↔ Type Consistency Anchors

Valibot schemas are bound to the hand-written types they validate, in the
schema file (never the other way around):

```typescript
// parser/service/tailordb/schema.ts
const TailorDBFieldSchema: v.GenericSchema<TailorDBFieldOutput> = v.lazy(() => ...);
```

`configure/types/type-compatibility.test.ts` additionally asserts that
configure's full builder types extend the minimal structural interfaces.

## vinfer Generation

**Command:** `pnpm -C packages/sdk generate`

**Config:** `packages/sdk/vinfer.config.ts`

- Source: Valibot schemas in `src/parser/**/schema.ts` (exports ending with `Schema` suffix)
- Output: `src/types/[dir].generated.ts` (directory name becomes filename)
- `map` option renames types (e.g., `TailorDBTypeSchema` → `TailorDBTypeRaw`)
- `v.description("...")` on schema fields generates TSDoc comments in output types
- Each schema produces both Input and Output type variants

A recursive schema needs a type annotation somewhere to satisfy TypeScript's
"implicitly has type any because it is referenced in its own initializer"
check, but _where_ that annotation goes changes how well vinfer resolves the
recursion:

- **Best — a getter, annotated only at the property's return type**, not on
  the schema constant itself: `get fields(): v.GenericSchema<Record<string,
Shape>> { return v.record(v.string(), ThisSchema); }`. When the recursive
  property is a required key, vinfer terminates the recursion in a named
  self-reference rather than `any`. See `TailorFieldSchema`
  (`parser/service/field/schema.ts`). As of `vinfer@0.1.3`, this no longer
  inlines a redundant copy of the shape before the self-reference (it used to,
  dropping `v.description` TSDoc in that copy), and a recursive schema reached
  through a schema vinfer generates no type for — an unexported intermediate,
  or one in another output file — is now referenced by name instead of
  collapsing to bare `any` (see `input` / `output` in
  `types/resolver.generated.ts`, which now import `TailorField` from
  `./field.generated`).

- **Degraded but usable — same getter pattern, on an optional property**:
  vinfer still resolves only one level deep here, then falls back to `any` for
  the rest — this specific case is not fixed by 0.1.3. When annotating the
  return type for an optional recursive property, use valibot's own
  `v.OptionalSchema<Wrapped, Default>` (or `v.NullableSchema<...>` for a
  nullable one) rather than a generic `v.GenericSchema<T | undefined>` union —
  vinfer reads the _schema wrapper type_ to decide whether to render the
  generated key as `key?:` or `key:`, and a `v.GenericSchema<T | undefined>`
  annotation does not read as "optional" to it, producing a `key:` (required)
  at that level while every other level of the same recursion renders `key?:`
  (optional) — a self-inconsistent type that then fails structural checks
  against itself one recursion step down. See `SCIMAttributeSchema`
  (`parser/service/auth/schema.ts`, `subAttributes`) for the working form —
  its own `subAttributes` field still bottoms out at `any[] | null | undefined`
  one level down.
- **Do not** annotate the schema constant itself (`export const Foo:
v.GenericSchema<T> = ...`) or a `v.lazy()` callback's return type — both
  collapse vinfer's generation into a broken self-alias (`type Foo = Foo`) or
  immediate `any` with zero levels resolved.

## valibot Isolation Guard

`pnpm -C packages/sdk check:valibot-isolation` (part of `pnpm check`) walks the
import closure of every `package.json#exports` entry in `dist/` and fails if
any entry other than `./cli` can reach valibot — in its rolled-up `.d.mts` graph
(type level) or its `.mjs` graph (runtime level).

## Workflow When Changing Valibot Schemas

1. Edit `src/parser/**/schema.ts`
2. Run `pnpm -C packages/sdk generate` to regenerate `src/types/*.generated.ts`
3. Update the owning layer's pure type module if new derived types are needed
4. Run `pnpm check` to verify build, lint, typecheck, and valibot isolation
