# Migrating to v2

Start with [`tailor-sdk upgrade --from <old-version>`](../cli/upgrade.md). It applies the v2 migrations that can be rewritten mechanically, then leaves you with a smaller set of changes to review or finish by hand.

For sections marked **Codemod available**, prefer running `tailor-sdk upgrade --from <old-version>` and use this guide to review the generated diff or handle unsupported edge cases. Do not hand-apply those migrations before trying the codemod. Sections marked **Manual only** require hand changes after the upgrade.

## Recommended upgrade flow

1. Update your SDK packages to the v2 version.
2. Run `tailor-sdk upgrade --from <old-version>`.
3. Review the codemod-backed sections below against the generated diff.
4. Work through the manual-only sections.
5. Run your project type check and tests.

## Codemod coverage

| Area                                | Automation        | What to review                                                                                                                          |
| ----------------------------------- | ----------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `defineGenerators()` configuration  | Codemod available | Built-in generator tuples become `definePlugins()` calls with dedicated plugin imports.                                                 |
| CLI and script command names        | Codemod available | `apply`, `crash-report`, `tailor-sdk-skills`, and wrapped `function test-run --arg` JSON are rewritten in common script and docs files. |
| Principal types and resolver caller | Codemod available | Principal type names become `TailorPrincipal`; resolver bodies receive `caller` instead of `user`.                                      |
| `auth.invoker("name")`              | Codemod available | Literal machine-user names become bare strings; dynamic expressions remain manual.                                                      |
| `Tailordb.*` ambient namespace      | Codemod available | Capital-cased `Tailordb.*` type references become lowercase `tailordb.*`.                                                               |
| Test mock helpers                   | Manual only       | Replace `setup*Mock` helpers with the `tailor-runtime` Vitest environment and `mockX()` controllers.                                    |
| Workflow job trigger tests          | Manual only       | Update job trigger mocks and full-chain local workflow tests for the v2 trigger behavior.                                               |
| File streaming                      | Manual only       | Replace `openDownloadStream` consumers with `downloadStream` and `ReadableStream` handling.                                             |
| Ambient global types                | Manual only       | Explicitly activate globals or replace `tailor.*` references with runtime wrappers.                                                     |
| Plugin namespace/default imports    | Manual only       | Rewrite namespace/default plugin references to named imports from dedicated plugin subpaths.                                            |

## Generator plugins (`defineGenerators()` -> `definePlugins()`)

**Automation:** Codemod available. Run `tailor-sdk upgrade --from <old-version>` first.

v2 uses `definePlugins()` for built-in code generation plugins. The codemod rewrites `defineGenerators()` tuple syntax for the built-in generators, renames the SDK import, and adds plugin imports from their dedicated subpaths.

```ts
// Before
import { defineGenerators } from "@tailor-platform/sdk";

export const generators = defineGenerators(
  ["@tailor-platform/kysely-type", { distPath: "./generated/db.ts" }],
  ["@tailor-platform/enum-constants", { distPath: "./generated/enums.ts" }],
);
```

```ts
// After
import { definePlugins } from "@tailor-platform/sdk";
import { enumConstantsPlugin } from "@tailor-platform/sdk/plugin/enum-constants";
import { kyselyTypePlugin } from "@tailor-platform/sdk/plugin/kysely-type";

export const generators = definePlugins(
  kyselyTypePlugin({ distPath: "./generated/db.ts" }),
  enumConstantsPlugin({ distPath: "./generated/enums.ts" }),
);
```

After the codemod runs, review any remaining `defineGenerators()` calls. Custom generators need a plugin implementation instead; see [Custom Plugins](../plugin/custom.md).

## CLI and script command names

**Automation:** Codemod available. Run `tailor-sdk upgrade --from <old-version>` first.

The v2 codemods rewrite common CLI changes in `package.json` scripts, shell scripts, CI YAML, and Markdown snippets:

| Before                                                     | After                                            |
| ---------------------------------------------------------- | ------------------------------------------------ |
| `tailor-sdk apply`                                         | `tailor-sdk deploy`                              |
| `tailor-sdk crash-report`                                  | `tailor-sdk crashreport`                         |
| `tailor-sdk-skills`                                        | `tailor-sdk skills install`                      |
| `tailor-sdk function test-run ... --arg '{"input":{...}}'` | `tailor-sdk function test-run ... --arg '{...}'` |

Review scripts that construct commands dynamically, because those may not appear as literal text for the codemod to rewrite.

## Principal types and resolver caller

**Automation:** Codemod available. Run `tailor-sdk upgrade --from <old-version>` first.

v2 unifies the principal types. The codemod rewrites SDK imports of `TailorUser`, `TailorActor`, and `TailorInvoker` to `TailorPrincipal`, and updates resolver body destructuring from `user` to `caller` where it can do so safely.

```ts
// Before
import { createResolver, t, type TailorUser } from "@tailor-platform/sdk";

export default createResolver({
  name: "getUser",
  operation: "query",
  input: t.object({ id: t.string() }),
  output: t.object({ id: t.string() }),
  body: ({ input, user }) => ({ id: user.id }),
});

export const getId = (user: TailorUser) => user.id;
```

```ts
// After
import { createResolver, t, type TailorPrincipal } from "@tailor-platform/sdk";

export default createResolver({
  name: "getUser",
  operation: "query",
  input: t.object({ id: t.string() }),
  output: t.object({ id: t.string() }),
  body: ({ input, caller }) => ({ id: caller.id }),
});

export const getId = (user: TailorPrincipal) => user.id;
```

The codemod also replaces standalone `unauthenticatedTailorUser` references with `null`. Review any remaining `unauthenticatedTailorUser` references after the upgrade; property access such as `unauthenticatedTailorUser.id` needs a user-specific fallback.

Review tests and fixtures too. Resolver `.body()` contexts now use `caller`, and unauthenticated resolver calls use `caller: null` instead of `user: unauthenticatedTailorUser`.

```ts
// Before
const result = await resolver.body({
  input,
  user: unauthenticatedTailorUser,
  env: {},
});

// After
const result = await resolver.body({
  input,
  caller: null,
  env: {},
});
```

## Auth invoker values

**Automation:** Codemod available. Run `tailor-sdk upgrade --from <old-version>` first.

`auth.invoker("machine-user")` is removed in favor of passing the machine-user name directly as a string.

```ts
// Before
await orderWorkflow.trigger(input, { authInvoker: auth.invoker("manager-machine-user") });

// After
await orderWorkflow.trigger(input, { authInvoker: "manager-machine-user" });
```

The codemod rewrites literal string arguments and removes the `auth` import when it is no longer used. Calls with variables or template literals are left unchanged so you can decide the right value explicitly.

## TailorDB ambient namespace casing

**Automation:** Codemod available. Run `tailor-sdk upgrade --from <old-version>` first.

The capital-cased `Tailordb.*` ambient namespace is removed. Use the lowercase `tailordb.*` namespace instead.

```ts
// Before
function takeClient(client: Tailordb.Client): void {
  void client;
}

// After
function takeClient(client: tailordb.Client): void {
  void client;
}
```

This only changes the namespace casing. If your project still relies on ambient TailorDB types after the codemod, also follow [Ambient global types](#ambient-global-types).

## Test mock helpers

**Automation:** Manual only. Do this after `tailor-sdk upgrade --from <old-version>`.

The `setup*Mock` helpers from `@tailor-platform/sdk/test` are removed. Replace them with the `tailor-runtime` Vitest environment and its `mockX()` controllers, acquired with [`using`](../testing.md#acquiring-mocks-with-using) so they reset automatically.

| Deprecated (`@tailor-platform/sdk/test`)    | Replacement                                                                                              |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `setupTailordbMock(resolver?)`              | `using db = mockTailordb()` — see [TailorDB Mock](../testing.md#tailordb-mock)                           |
| `setupWorkflowMock(handler)`                | `using wf = mockWorkflow()` — see [Workflow Mock](../testing.md#workflow-mock)                           |
| `setupWaitPointMock({ onWait, onResolve })` | `using wf = mockWorkflow()` — see [Jobs that wait on approval](../testing.md#jobs-that-wait-on-approval) |
| `setupInvokerMock(invoker)`                 | Pass `invoker` to `.body()`, or spy on `getInvoker` (see below)                                          |
| `setupTailorErrorsMock()`                   | Nothing — the `tailor-runtime` environment injects the error classes automatically                       |

**TailorDB** — drive responses with `setQueryResolver` / `enqueueResult` and assert on `executedQueries`:

```typescript
// Before
const mock = setupTailordbMock((query) => (query.includes("SELECT") ? [{ id: "1" }] : []));
expect(mock.executedQueries).toHaveLength(1);

// After
using db = mockTailordb();
db.setQueryResolver((query) => (query.includes("SELECT") ? [{ id: "1" }] : []));
expect(db.executedQueries).toHaveLength(1);
```

**Workflow** — drive job results with `setJobHandler` and assert on `triggeredJobs`:

```typescript
// Before
const mock = setupWorkflowMock((jobName) =>
  jobName === "validate-order" ? { valid: true } : null,
);
expect(mock.triggeredJobs).toEqual([{ jobName: "validate-order", args: { orderId: "o-1" } }]);

// After
using wf = mockWorkflow();
wf.setJobHandler((jobName) => (jobName === "validate-order" ? { valid: true } : null));
expect(wf.triggeredJobs).toEqual([{ jobName: "validate-order", args: { orderId: "o-1" } }]);
```

**Wait points** — `setupWaitPointMock`'s `onWait` / `onResolve` become `setWaitHandler` / `setResolveHandler` on the same `mockWorkflow()` controller; the `waitCalls` / `resolveCalls` assertion shape is unchanged.

**Invoker** — there is no dedicated controller. For unit tests against the TypeScript source, pass `invoker` directly to `.body()`; for tests against the bundled output, spy on `getInvoker`:

```typescript
// Before
setupInvokerMock(myInvoker);
const result = await resolver.body({ input, user, env });

// After (unit test)
const result = await resolver.body({ input, caller, env, invoker: myInvoker });

// After (bundle test)
const rawInvoker = myInvoker
  ? {
      id: myInvoker.id,
      type: myInvoker.type,
      workspaceId: myInvoker.workspaceId,
      attributes: myInvoker.attributeList,
      attributeMap: myInvoker.attributes,
    }
  : null;
vi.spyOn(globalThis.tailor.context, "getInvoker").mockReturnValue(rawInvoker);
```

**Tailor errors** — `setupTailorErrorsMock()` has no replacement; the `tailor-runtime` environment always provides the error classes, so delete the call.

## Workflow job trigger tests

**Automation:** Manual only. Do this after `tailor-sdk upgrade --from <old-version>`.

Workflow job `.trigger()` now matches the platform workflow runtime: it dispatches another job and returns that job's output value directly. It no longer runs registered job bodies by itself in local tests.

Update local tests in two common places:

- If a test spies on another job's `.trigger()`, return the job output directly.
- If a test uses `workflow.mainJob.trigger(...)` to exercise a whole workflow chain with real job bodies, switch it to `runWorkflowLocally(...)` from `@tailor-platform/sdk/vitest`.

```ts
// Before
using _validateSpy = vi.spyOn(validateOrder, "trigger").mockResolvedValue({
  valid: true,
});

const result = await orderWorkflow.mainJob.trigger({ orderId: "o-1" });
```

```ts
// After
import { runWorkflowLocally } from "@tailor-platform/sdk/vitest";

using _validateSpy = vi.spyOn(validateOrder, "trigger").mockReturnValue({
  valid: true,
});

const result = await runWorkflowLocally(orderWorkflow, { orderId: "o-1" });
```

Use `mockWorkflow()` when the code under test should observe mocked platform workflow responses. Use `runWorkflowLocally()` only when the test should execute the workflow's real job bodies locally.

## File streaming (`openDownloadStream` → `downloadStream`)

**Automation:** Manual only. Do this after `tailor-sdk upgrade --from <old-version>`.

`openDownloadStream` is removed in favor of `downloadStream`, which takes the same four arguments but hands you a standard `ReadableStream<Uint8Array>` body plus the metadata up front, instead of an async iterator of typed stream events.

Key consumer-side differences:

- Read the file with the standard `ReadableStream` reader (or `for await` where your runtime supports it) rather than branching on `type: "metadata" | "chunk" | "complete"`.
- `metadata` is available immediately on the result — you no longer wait for a leading `metadata` event.
- There is no `complete` event and no `close()` to call; the reader settles on its own when the stream ends.

```ts
// Before — openDownloadStream (removed)
const stream = await file.openDownloadStream("my-namespace", "Document", "attachment", recordId);
let metadata;
const chunks: Uint8Array[] = [];
for await (const item of stream) {
  if (item.type === "metadata") metadata = item.metadata;
  else if (item.type === "chunk") chunks.push(item.data);
  // item.type === "complete" ends the loop
}
await stream.close();
```

```ts
// After — downloadStream
const { body, metadata } = await file.downloadStream(
  "my-namespace",
  "Document",
  "attachment",
  recordId,
);
const chunks: Uint8Array[] = [];
const reader = body.getReader();
for (;;) {
  const { done, value } = await reader.read();
  if (done) break;
  chunks.push(value);
}
```

## Ambient global types

**Automation:** Manual only. Do this after `tailor-sdk upgrade --from <old-version>`.

The SDK no longer activates the ambient `tailor.*` / `tailordb.*` types implicitly. After upgrading, code that relies on them — for example `tailor.iconv.convert(...)` or `new tailordb.Client(...)` — stops type-checking unless you activate the globals yourself (see [Activating the global types](../runtime.md#activating-the-global-types)). Pick one of:

- **Option A — per-file side-effect import.** Add `import "@tailor-platform/sdk/runtime/globals";` to each file that references the globals. Use this when only a few files touch them.
- **Option B — project-wide via `tsconfig.json`.** Add `"@tailor-platform/sdk/runtime/globals"` to `compilerOptions.types` so every file in the project sees the ambient types. Use this when the globals are spread across many files.
- **Option C (recommended where available) — drop the globals.** For the `tailor.*` namespaces, replace global references with the typed wrappers from `@tailor-platform/sdk/runtime` so no activation is needed at all:

  ```ts
  // Before — relies on the ambient global
  const client = new tailor.idp.Client({ namespace: "my-namespace" });

  // After — typed wrapper, no globals required
  import { idp } from "@tailor-platform/sdk/runtime";
  const client = new idp.Client({ namespace: "my-namespace" });
  ```

  The `tailordb.*` globals (e.g. `tailordb.Client`, `tailordb.QueryResult`) have no wrapper equivalent, so code that uses them still needs Option A or B.

## Plugin imports from `@tailor-platform/sdk/cli`

**Automation:** Manual only for namespace/default imports. Do this after `tailor-sdk upgrade --from <old-version>`.

Use dedicated plugin subpaths instead of loading built-in plugins through `@tailor-platform/sdk/cli`. If you reference a plugin through a namespace or default import (for example, `import * as cli from "@tailor-platform/sdk/cli"`), rewrite it to a named import of the dedicated subpath by hand.

| Plugin                | Import path                                  |
| --------------------- | -------------------------------------------- |
| `kyselyTypePlugin`    | `@tailor-platform/sdk/plugin/kysely-type`    |
| `enumConstantsPlugin` | `@tailor-platform/sdk/plugin/enum-constants` |
| `fileUtilsPlugin`     | `@tailor-platform/sdk/plugin/file-utils`     |
| `seedPlugin`          | `@tailor-platform/sdk/plugin/seed`           |
