### Minor Changes

- [#2669](https://github.com/tailor-platform/sdk/pull/2669) [`f59f06e`](https://github.com/tailor-platform/sdk/commit/f59f06e14ecc3c22553d5da7b13b87dd7376c059) Thanks [@dqn](https://github.com/dqn)! - The `tailor` CLI and its command groups, such as `tailor tailordb` and `tailor workspace`, and the setup, seed, and TailorDB ERD plugins now exit with code 2 when run without a subcommand and given an unknown option or an invalid option value, including one set through its environment variable. They previously printed their help or a warning, or ran their default subcommand, and exited with 0. A script or CI job that passes a mistyped option after a group name, such as `tailor workspace --bogus`, now fails with 2 instead of printing a warning and exiting with 0. `--no-json` and `--no-verbose` now turn JSON output and verbose logging off, where they were previously ignored with a warning, so `--no-json` also turns off the JSON output an AI coding agent gets by default. `--no-verbose` and `--verbose=false` also override `DEBUG=true` and `RUNNER_DEBUG=1`, which previously kept verbose logging on. Likewise, setting `logger.verbose` from `@tailor-platform/sdk/cli` overrides them, and setting it to `undefined` defers to them.

- [#2576](https://github.com/tailor-platform/sdk/pull/2576) [`07611f5`](https://github.com/tailor-platform/sdk/commit/07611f5a28210bcb50b2234b34fee6faaaa1d304) Thanks [@toiroakr](https://github.com/toiroakr)! - `tailor setup ci preview` takes `--require <ready|label>` instead of `--require-preview-label`. By default every pull request now gets a preview, draft pull requests included, which the generated workflow used to skip. `--require ready` skips draft pull requests and also triggers on `ready_for_review`, so a draft that is marked ready for review gets its preview right away instead of waiting for the next push. `--require label` deploys only pull requests labeled `tailor:preview`, as `--require-preview-label` did, and now also for a labeled draft. The requirement is recorded in `.github/tailor.lock` as `require`, so `tailor setup update` regenerates the same workflow.
  
  `--require-preview-label` is removed: use `--require label`. `setup` remains a beta command, so this ships as an immediate change rather than going through a deprecation cycle. A preview target recorded before this change is read by `tailor setup update` as `--require ready`, or as `--require label` if it required the label: the first keeps skipping drafts and gains the `ready_for_review` trigger, and the second now also deploys a labeled draft. To deploy drafts as well, run `tailor setup ci preview` again without `--require`.

### Minor Changes

- [#2601](https://github.com/tailor-platform/sdk/pull/2601) [`00c5613`](https://github.com/tailor-platform/sdk/commit/00c56132166f4fec563d82b686afc3bad82f8ef2) Thanks [@dqn](https://github.com/dqn)! - The workflows `tailor setup ci` generates now run on GitHub Enterprise Server: the plan comment, change detection, preview deployment, and ERD preview comment call the GitHub API of the server the workflow runs on instead of github.com. Run `tailor setup update` to regenerate existing workflows.
  
  GitHub Enterprise Server does not support the artifact upload the ERD preview uses, so pass `--ghes` with `--erd-preview` to `tailor setup ci branch` there: each ERD viewer is then uploaded as a zip file, and the pull request comment links to the workflow run. The GitHub Actions guide lists the runner and action setup GitHub Enterprise Server needs.

- [#2643](https://github.com/tailor-platform/sdk/pull/2643) [`f5c304f`](https://github.com/tailor-platform/sdk/commit/f5c304f8867d6416ccfa315694163d2e77a69e73) Thanks [@dqn](https://github.com/dqn)! - Add `tailor setup ci env --check`, which reads GitHub with `gh` and reports which secrets and variables each GitHub Environment used by the generated workflows still lacks. It fails when a required entry is missing, only reports missing optional ones, and prints the `gh` commands that set the missing entries together with where each value comes from. Entries set on the repository or organization count as registered, and an entry registered as the wrong kind (a secret where the workflow reads a variable) is pointed out. When `gh` is not installed, not logged in, or cannot read the repository's secrets and variables, the check says so instead of reporting entries as missing. The next steps printed after `tailor setup ci branch`, `tag`, and `preview` now suggest running it.
  
  When the `origin` remote is not on github.com, `tailor setup ci env` now names the repository that `gh repo view` reports, with its host on GitHub Enterprise Server, instead of leaving it to `gh` at run time: the printed `gh` commands pass that host, and the Terraform output sets `GITHUB_BASE_URL` to it. `--check` prints its commands for the host it checked. When `gh` cannot tell the repository, the output says how to point `gh` and Terraform at a GitHub Enterprise Server host.

- [#2624](https://github.com/tailor-platform/sdk/pull/2624) [`34771b0`](https://github.com/tailor-platform/sdk/commit/34771b0dc54beb62062cfc03a961799e72269766) Thanks [@toiroakr](https://github.com/toiroakr)! - The preview workflow generated by `tailor setup ci preview` now gives each per-PR workspace a 7-day expiry (`ttl: 7d` on `tailor-preview-deploy`) that every push to the pull request restarts. When a pull request is closed, `tailor-preview-cleanup` also deletes the other expired preview workspaces of the same workspace name in the folder (`TAILOR_PLATFORM_FOLDER_ID`, or directly under the organization when unset), so a preview whose own cleanup never ran no longer stays forever. You can edit `ttl` and re-running `tailor setup` keeps your value.
  
  Run `tailor setup update` to add this to an existing preview workflow. After that, a pull request left idle for more than 7 days has its workspace deleted while it is still open, and the next push creates a fresh one, so the data reviewers added to it is lost. The generated preview workflow needs `tailor-platform/actions` v2.6.0 or later, which `tailor setup update` also pins.

- [#2660](https://github.com/tailor-platform/sdk/pull/2660) [`df71b44`](https://github.com/tailor-platform/sdk/commit/df71b44d2c03d8f767bea5448ee64bb1f114dcfb) Thanks [@dqn](https://github.com/dqn)! - The `tailor` CLI, the setup, seed, and TailorDB ERD plugins, `create-sdk`, and the codemod CLI now exit with code 2 when they reject the command line itself, such as an unknown option or subcommand, an unexpected argument, or an option value that fails validation, so scripts and agents can tell a mistyped command from one that failed while running, which still exits with 1. A command that only warns about an unknown option or an extra argument, such as `create-sdk`, keeps running as before. A script that checks for exactly 1 after a mistyped command needs to accept 2. `runMain` and `runCommand` from `@tailor-platform/sdk/cli` follow the same rule, so a CLI plugin built on them exits with 2 for these errors, and `runCommand` reports them with `exitCode` 2.

- [#2572](https://github.com/tailor-platform/sdk/pull/2572) [`610a2ca`](https://github.com/tailor-platform/sdk/commit/610a2ca310a687afe5d0da77e88ddc8196090d55) Thanks [@dqn](https://github.com/dqn)! - `tailor setup ci branch`, `tag`, and `preview` accept `--package-manager` (`pnpm`, `npm`, `yarn`, or `bun`) to choose the package manager the generated workflow uses, for example to generate the workflow before the lockfile exists. `.github/tailor.lock` records the choice, and `tailor setup update` keeps it.
  
  Without the flag, the package manager is still detected from the lockfile at the repository root (now including `npm-shrinkwrap.json`), and otherwise from the `packageManager` or `devEngines.packageManager` field of the root `package.json`. When neither names one, `setup ci` and `setup update` stop with an error instead of silently choosing npm, which produced a workflow that failed in CI without a lockfile at the repository root. `setup` remains a beta command, so this ships as an immediate change rather than going through a deprecation cycle.

- [#2587](https://github.com/tailor-platform/sdk/pull/2587) [`65dad3e`](https://github.com/tailor-platform/sdk/commit/65dad3e34b8fc9d146ffdd9c2efb5045303fc9b7) Thanks [@dqn](https://github.com/dqn)! - Seed the workspace from the generated deploy workflows: `tailor setup ci branch`, `tag`, and `preview` take `--seed` and `--seed-dataset <name>` (repeatable, implies `--seed`), which add a `tailor-seed` step after the deploy step. Branch and tag targets validate the selected data with `tailor seed validate --upsert` before deploy and apply it with `tailor seed apply --upsert` after deploy. Branch targets also validate in the PR or dry-run plan job; tag targets use the plan job's validation before deploy. Preview workspaces validate the data after deploy and apply it with `--truncate --yes`. Setup stops when the config has no `seedPlugin`, `seedPlugin` has no `machineUserName` or `distPath`, the seed data directory is missing, or a dataset is unknown, and seeding is available for targets that deploy one app. `tailor setup update` keeps the flags, and `tailor setup check` reports a seeding target whose `seedPlugin` settings no longer allow it.

## 0.2.0

### Minor Changes

- [#2168](https://github.com/tailor-platform/sdk/pull/2168) [`aef699b`](https://github.com/tailor-platform/sdk/commit/aef699b36f5b0957747f34a327b0e19f1e47ba3a) Thanks [@dqn](https://github.com/dqn)! - Move the `tailor setup` commands into the optional `@tailor-platform/sdk-plugin-setup` CLI plugin.
  
  `setup` generates GitHub repository automation, which not every project uses, but its workflow templates and its `@croct/json5-parser` / `json5` dependencies shipped with the SDK for everyone. Splitting it out follows the same CLI plugin mechanism as `tailor tailordb erd`.
  
  To keep using `tailor setup <command>`, install the plugin next to the SDK:
  
  ```bash
  npm install -D @tailor-platform/sdk-plugin-setup
  ```
  
  The commands, options, generated files, and the `.github/tailor.lock` format are unchanged.
